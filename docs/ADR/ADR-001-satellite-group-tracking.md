# ADR-001: Группа спутников, выбор текущего КА и сопровождение

**Дата:** 2026-03-22  
**Статус:** Accepted

---

## Описание механизма

### Задача

Станция наблюдения видит спутники CubeSat по очереди — каждый пролетает над горизонтом на несколько минут, потом уходит. Иногда несколько КА видны одновременно. Система должна:

- Определять, какие КА сейчас доступны или скоро появятся.
- Показывать их оператору списком.
- Автоматически выбирать «главный» КА для отображения.
- Позволять оператору взять конкретный КА на сопровождение (направить антенну, начать приём).
- Корректно завершать сопровождение когда КА уходит за горизонт.

### Основные понятия

**Группа** — множество КА, чьи пролёты попадают в скользящее окно `[now, now + 1 мин]`. Формируется на бэкенде каждые 5 секунд. Пролёт попадает в группу если `AOS < now+1мин && LOS > now`. Если ни один пролёт не попадает — в группу ставится один КА с ближайшим будущим AOS (заглушка). Группа — это то, что оператор видит в таблице правой панели.

**Primary** — КА из группы, который автоматически выбран системой как текущий. Его трасса подсвечена на карте, его данные показаны в SkyView. Выбирается по приоритету: ручной выбор → видимый с наибольшей длительностью сеанса → любой с наибольшей длительностью.

**Selected** — КА, выделенный оператором в таблице (клик по строке). По умолчанию совпадает с primary, но оператор может кликнуть на другую строку. Selected определяет: какая жёлтая/циановая трасса видна на карте, какой маркер на SkyView, какие данные в overlay-панели. Никак не влияет на антенну.

**Tracking** — КА, взятый на сопровождение оператором (кнопка «⊕ Сопров.»). Означает: антенна ведёт этот КА, идёт приём. На карте — отдельный слой (красно-зелёная трасса + пурпурная зона видимости), Az/El индикаторы показывают направление, нижняя панель переключается на вкладку «Сопровождение». Tracking и selected — независимые состояния: можно листать таблицу, не трогая антенну.

### Как устроен поток данных

Вся орбитальная математика — на бэкенде (Go). Фронтенд не знает про SGP4, TLE, системы координат. Он получает готовые `{lat, lon, az, el, range, ...}` через SSE и рисует.

Бэкенд работает в трёх циклах:
- **Каждую секунду** — пересчёт позиций всех КА в группе (SGP4 → координаты + AER + зона видимости) → SSE-событие `satellite_state_update`.
- **Каждые 30 секунд** — пересчёт наземных трасс (past/future сегменты) → включаются в тот же `satellite_state_update`.
- **Каждые 5 секунд** — проверка скользящего окна, пересчёт группы и primary → SSE-события `satellite_group_update` и `satellite_change` при изменениях.

На фронтенде единственный `SatelliteStateManager` принимает все данные от SSE и раздаёт UI-компонентам через Observer pattern: EarthView (карта), SkyView (азимутальная проекция), Az/El (индикаторы), RightPanelTable (таблица группы).

### Жизненный цикл сопровождения

1. **Нет сопровождения.** Система в обзорном режиме. Primary выбирается автоматически. Оператор листает таблицу (selected), смотрит трассы на карте.
2. **Оператор нажимает «⊕ Сопров.»** Фронтенд отправляет `POST /api/tracking/current`. Бэкенд сохраняет выбор (`manualSelection`), отправляет подтверждение через SSE конкретному клиенту (`client_state_restore`). На карте появляется tracking-слой, нижняя панель переключается на «Сопровождение».
3. **Во время сеанса.** Tracking фиксирован. Оператор может кликать по другим строкам (selected меняется), tracking не трогается. Позиции приходят каждую секунду — Az/El обновляются, карта перерисовывается.
4. **Завершение.** Два варианта:
   - **Ручной сброс** — кнопка «✕ Сброс» → `POST /api/tracking/reset` → tracking-слой очищается, панель → «Обзор».
   - **Авто-сброс** — КА ушёл за горизонт (`now > LOS`), бэкенд обнаруживает это в `updateGroup()` через ≤ 5 сек, рассылает `satellite_change {reason: "tracking_ended"}` → тот же результат.
5. **Возврат в обзор.** Primary выбирается заново автоматически. Цикл повторяется.

## Часть I. Решения и обоснования

### Почему скользящее окно, а не список всех видимых

Наивный подход — показывать все КА с `El > 0°` — порождает проблему: состав списка дёргается каждую секунду (КА появляется над горизонтом, тут же пропадает на краю зоны). Скользящее окно `[now, now + 1 мин]` даёт предсказуемую группу: КА появляется в таблице за минуту до AOS, остаётся до LOS. Смена состава — не чаще раза в 5 секунд (интервал `groupTicker`). UI стабильный, оператор не теряет контекст.

Размер окна в 1 минуту — компромисс: достаточно для подготовки к сеансу, но не засоряет таблицу далёкими пролётами.

### Почему два независимых состояния: selected и tracking

Одного «текущего КА» не хватает. Оператор хочет:

- **Просматривать** разные спутники в таблице (кликать, изучать параметры, смотреть трассу) — это `selected`.
- **Вести** один конкретный КА (антенна направлена, идёт приём) — это `tracking`.

Если слить в одно — клик по другой строке таблицы переключит антенну. Раздельные состояния позволяют листать таблицу, не прерывая сопровождение. На карте и SkyView видны оба слоя одновременно: selected — жёлтая/циановая трасса, tracking — красно-зелёная.

### Почему вся математика на бэкенде

SGP4-пропагация, AER, зоны видимости, наземные трассы — всё на Go. Фронтенд получает готовые `{lat, lon, az, el, ...}` и только рисует. Причины:

- Один источник истины — нет рассинхрона между «что видит карта» и «что видит SkyView».
- Go считает SGP4 для всей группы за < 1 мс. Нет смысла грузить браузер.
- Фронтенд — vanilla JS без фреймворков. Тащить SGP4 в браузер — отдельная библиотека, отдельные баги.

### Почему SSE, а не WebSocket

Поток данных однонаправленный: сервер → клиент. Для команд (сопровождение, сброс) достаточно `POST`. SSE даёт:

- Автопереподключение средствами браузера (EventSource).
- Проще на сервере: обычный HTTP handler, без upgrade, без ping/pong.
- Кеширование последних событий в Hub — новый клиент получает данные мгновенно.

### Почему per-client tracking, а не глобальный

Если один оператор поставил КА на сопровождение, другой не должен видеть чужое сопровождение. `satellite_group_update` рассылается всем с `tracking_id=0`. Персональный `tracking_id` доставляется через направленное событие `client_state_restore` конкретному `client_id`. Каждая вкладка браузера — отдельный клиент (UUID в `sessionStorage`).

## Часть II. Сквозные задачи

### 1. Формирование группы: от TLE до таблицы на экране

**Бэкенд.** `PassService` раз в час пересчитывает пролёты для всех КА из конфигурации (TLE-группы). Результат — массив `[]*tracker.Pass` с полями `NoradID, AOS, LOS, Duration, SkyPath`. `SatelliteTrackingService` каждые 5 секунд берёт этот кеш и применяет `FindConcurrentPasses()`:

- Условие попадания: `AOS < now + 1 мин && LOS > now`.
- Каждый КА получает флаг `IsVisible = (AOS ≤ now ≤ LOS)`.
- Сортировка по AOS, при равенстве — по NoradID (стабильный порядок).
- Если окно пустое — подставляется один КА с ближайшим будущим AOS (заглушка, `IsVisible=false`, `IsSubstitute=true`). Флаг `IsSubstitute` отличает подстановку от честного ожидания AOS в пределах окна.

Затем выбирается primary — см. §2.

**Change detection.** Для определения необходимости рассылки используется `GroupEntries` — слайс структур `{NoradID, IsVisible, AOS, LOS}`, отсортированный по NoradID. Сравнение `GroupEntriesChanged(old, new)` обнаруживает не только смену состава группы, но и:
- переход видимости (`IsVisible: true→false` при LOS, `false→true` при AOS);
- замену пролёта тем же КА (следующий виток — другие AOS/LOS).

Если данные группы или primary изменились — `SatelliteTrackingService` обновляет пропагаторы для каждого КА в группе и рассылает `satellite_group_update` через SSE Hub. Если primary_id не изменился, но данные пролёта изменились — дополнительно рассылается `satellite_change {reason: "auto"}`, чтобы фронтенд обновил sky path и таблицу.

**Транспорт.** Событие `satellite_group_update` содержит: массив `satellites[]` (norad_id, sat_name, aos, los, duration, is_visible, предрассчитанные строки `ui_col_duration` и `ui_col_until`), `primary_id`, `time_window`.

**Фронтенд.** `SSEClient` передаёт данные в `SatelliteStateManager.setSatelliteGroup()`. StateManager обновляет `_satelliteGroup`, устанавливает `_selectedSatelliteId` из `primary_id` (если нет ручного выбора в таблице), уведомляет подписчиков через `SATELLITE_GROUP_UPDATE`. `RightPanelTable` перерисовывает таблицу: строки с именем КА, обратный отсчёт до AOS или время сеанса, подсветка active/selected.

### 2. Выбор текущего КА: от алгоритма primary до подсветки в UI

`SelectPrimarySatellite()` — чистая функция. Три приоритета, проверяются по порядку:

**Приоритет 1 — Ручной выбор.** Если `manualSelection` задан и этот КА присутствует в текущей группе — он primary. Ручной выбор устанавливается через API сопровождения.

**Приоритет 2 — Лучший из видимых.** Среди КА с `IsVisible=true` — тот, у кого наибольшая `Duration`. Логика: если над горизонтом несколько КА, приоритет у длинного сеанса — меньше шансов на переключение в ближайшие секунды.

**Приоритет 3 — Лучший из всей группы.** Если видимых нет — тот, у кого наибольшая `Duration` среди всех (включая будущие). Тай-брейк при равной длительности: меньший NoradID.

**Логика переключения в `updateGroup()`.** Решение о смене primary принимается в два этапа:

1. `ShouldSwitchPrimary(currentID, satellites, now)` — проверяет, нужно ли переключение:
   - Если текущий primary виден (`IsVisible=true`) и пролёт не завершён (`now ≤ LOS`) — **не переключать**, даже если в группе есть КА с большей длительностью. Это предотвращает преждевременную смену посреди активного сеанса.
   - Если текущий primary ожидает AOS в пределах окна (`!IsVisible && !IsSubstitute && now < AOS`) — **не переключать** (стабильное ожидание начала сеанса).
   - Если текущий primary — подстановка из следующего витка (`IsSubstitute=true`), или не найден в группе, или LOS прошёл — **переключить**.
2. `SelectPrimarySatellite()` вызывается **только** когда `ShouldSwitchPrimary` подтвердил необходимость переключения, либо при наличии ручного выбора (`manualSelection`).

Рассылается `satellite_change` с `reason=auto` и `satellite_group_update` с новым `primary_id`.

**На фронтенде.** `satellite_change` → `SSEClient._handleSatelliteChange()`:
- `reason=manual` — **игнорируется** (tracking устанавливается через `client_state_restore`, per-client).
- `reason=tracking_ended` — `clearTrackingSatellite()` + `setSelectedSatellite(..., forceNotify=true)`.
- `reason=auto/initial` — `setSelectedSatellite(..., forceNotify=true)`. `forceNotify=true` гарантирует срабатывание `SELECTED_CHANGE` даже если NORAD ID primary не изменился (бэкенд мог отправить `auto` при смене данных пролёта).

`satellite_group_update` → `StateManager.setSatelliteGroup()` — устанавливает selected из `primary_id` (если нет ручного выбора в таблице). Дополнительно `_hasPrimaryPassChanged()` сравнивает `(primary_id, aos, los, is_visible)` с предыдущим group_update: если данные изменились при том же NORAD — уведомляет `SELECTED_CHANGE`, чтобы SkyView перезагрузил sky path.

RightPanelTable перерисовывает подсветку строки, EarthView переключает жёлтую/циановую трассу, SkyView переключает маркер и стрелки направления.

### 3. Сопровождение КА: от нажатия кнопки до красно-зелёных трасс

**Включение.** Оператор нажимает «⊕ Сопров.» в правой панели. Фронтенд отправляет `POST /api/tracking/current {norad_id, client_id}`. `TrackingHandler` вызывает `SetManualSelection()` в `SatelliteTrackingService`:

- `manualSelection` ← norad_id.
- `ClientStateStore.SetTracking(clientID, noradID)` — сохранение per-client.
- Немедленный `updateGroup()` с `pendingManualBroadcast=true`.
- Всем — `satellite_group_update` (`tracking_id=0`, нейтральный).
- Конкретному клиенту — направленное `client_state_restore {tracking_id: noradID}`.

Фронтенд: `SSEClient` получает `client_state_restore` → `StateManager.setTrackingSatellite()` → событие `TRACKING_CHANGE`. EarthView рисует трасс-слой tracking (красная прошлая / зелёная будущая орбита + пурпурная зона видимости). SkyView рисует tracking-маркер. Az/El индикаторы показывают данные сопровождаемого КА. Нижняя панель автоматически переключается на вкладку «Сопровождение».

**Сброс вручную.** Кнопка «✕ Сброс» → `POST /api/tracking/reset {client_id}` → `ResetManualSelection()` → `manualSelection = nil` → `updateGroup()` → `client_state_restore {tracking_id: 0}`. Фронтенд: `clearTrackingSatellite()` → `TRACKING_CHANGE(null)` → слой tracking очищается, нижняя панель возвращается на вкладку «Обзор».

**Авто-сброс после LOS.** Каждые 5 сек `updateGroup()` проверяет: если `manualSelection` задан, но КА покинул скользящее окно, или окно пустое и `NoradInPostLosGap()` подтвердил что LOS уже прошёл (а не «ожидаем первый AOS») — сопровождение сбрасывается: `ClearTrackingForNorad()` для всех клиентов с этим NORAD, `manualSelection = nil`. Рассылается `satellite_change {reason: "tracking_ended"}`. Фронтенд обрабатывает аналогично ручному сбросу, с добавлением `setSelectedSatellite(..., forceNotify=true)` для обновления таблицы — primary мог не измениться, но слой tracking нужно перерисовать.

`NoradInPostLosGap()` нужен, чтобы отличить ситуацию «сеанс закончился, следующий AOS через 90 мин» от «первый виток ещё не начался, ждём AOS». В первом случае — сброс, во втором — сопровождение сохраняется.

### 4. Путь данных: от SGP4 до canvas.draw()

Раз в секунду `computeAndBroadcastState()` проходит по всем КА в `tracked` map:

**Бэкенд (на каждый КА):**

1. `Propagator.Propagate(now)` → координаты ECI (инерциальная СК).
2. `ECIToECEF` → `ECEFToLLA` → широта, долгота, высота.
3. `Observer.GetAER(eci)` → азимут, элевация, дальность от станции.
4. `GenerateVisibilityZoneFromLLA()` → 72 точки контура зоны видимости.
5. Раз в 30 сек: `GenerateDefaultGroundTrack()` → наземная трасса (past/future, сегменты с разрывами на антимеридиане).

Всё собирается в `satellite_state_update {positions[], tracks[]}` и уходит в Hub.

**Hub:** Кеширует последнее событие. Рассылает всем клиентам. При подключении нового клиента — отдаёт из кеша немедленно.

**Фронтенд:**

1. `SSEClient._handleStateUpdate()` — раскладывает `positions[]` по `StateManager.updatePosition()` для каждого КА. Если `tracks_included` — вызывает `updateTrack()`.
2. `StateManager` — обновляет `SatelliteState` в map, стреляет `POSITION` для selected-КА.
3. `EarthView` (подписчик `POSITION`) — вызывает `draw()`: проецирует `(lat, lon)` на canvas (экви-прямоугольная проекция), рисует три слоя: secondary (серый пунктир), selected (жёлтый), tracking (красно-зелёный). Маркеры, подписи, зону видимости.
4. `SkyView` (подписчик `POSITION`) — проецирует `(az, el)` в полярные координаты на canvas. Азимутальная проекция: центр = зенит, край = горизонт.
5. `Az/El` (подписчик `POSITION` + `TRACKING_CHANGE`) — стрелочные индикаторы: Azimuth-диск, Elevation-постамент.

## Часть III. Сценарии

### Сценарий 1: Рабочий сеанс оператора

**Обзор.** Оператор открывает приложение. SSE-соединение устанавливается. Из Hub-кеша приходит `satellite_group_update` — таблица в правой панели заполняется. В данный момент в группе 3 КА: два с будущими пролётами (обратный отсчёт до AOS), один виток уже идёт (длительность сеанса). Primary — видимый КА с наибольшей длительностью. Его трасса жёлтая на карте, оранжевый маркер на SkyView. Оператор кликает по другим строкам таблицы — подсветка переключается, трасса на карте меняется (selected). Нижняя панель — вкладка «Обзор» (FFT/SDR).

**Выбор КА.** Оператор решает принять сигнал от второго КА — кликает его строку, изучает параметры в overlay-панели (наклонение, период, AOS/LOS). Убеждается, что пролёт достаточно длинный.

**Сопровождение.** Нажимает «⊕ Сопров.». `POST /api/tracking/current` уходит на сервер. Через ~100 мс приходит `client_state_restore` — StateManager устанавливает `_trackingSatelliteId`. На карте появляется красно-зелёная трасса сопровождаемого КА и пурпурная зона видимости. SkyView показывает оба маркера (selected и tracking). Нижняя панель автоматически переключается на вкладку «Сопровождение» — Az/El индикаторы показывают направление на сопровождаемый КА. Оператор видит: антенна ведёт КА, водопад отображает сигнал.

**Во время сеанса.** Оператор может кликать по другим строкам таблицы (selected меняется), но tracking остаётся на месте — антенна не дёргается. Можно вернуться к сопровождаемому КА кликом — selected совпадёт с tracking, будут видны оба слоя.

**Завершение сеанса.** Когда `now > LOS` сопровождаемого КА и окно пустое, `NoradInPostLosGap()` возвращает `true`. Через ≤ 5 сек (тик `groupTicker`) бэкенд рассылает `satellite_change {reason: "tracking_ended"}`. Фронтенд: красно-зелёная трасса исчезает, нижняя панель возвращается на «Обзор», Az/El сбрасываются. Primary выбирается автоматически — следующий КА с наибольшей длительностью.

**Ручной сброс.** Если оператор хочет прервать сопровождение до LOS — нажимает «✕ Сброс». Аналогичный результат, но мгновенный.

### Сценарий 2: Два КА выходят на горизонт одновременно

КА-A (Duration 8 мин) и КА-B (Duration 12 мин) имеют AOS с разницей в 30 сек.

- **t₀:** `FindConcurrentPasses` находит КА-A (AOS < now+1мин). Группа: [КА-A]. Primary: КА-A (единственный).
- **t₀+30с:** КА-B тоже попадает в окно. Группа: [КА-A, КА-B]. Оба IsVisible. `ShouldSwitchPrimary(КА-A)` — пролёт КА-A ещё активен (`IsVisible=true`, `now ≤ LOS`) → **не переключать**. Primary остаётся КА-A. `satellite_group_update` с обновлённым составом (добавился КА-B).
- **t₀+8мин:** LOS КА-A. `ShouldSwitchPrimary(КА-A)` — пролёт завершён → **переключить**. `SelectPrimarySatellite` → КА-B (единственный видимый). `satellite_group_update` + `satellite_change {reason: auto}`.
- **t₀+12мин:** LOS КА-B. Группа пустеет. Подставляется ближайший будущий пролёт (`IsSubstitute=true`).

### Сценарий 3: Вторая вкладка браузера

Оператор ведёт КА на сопровождении. Открывает вторую вкладку. Новая вкладка:

1. `sessionStorage` генерирует новый `client_id` (UUID per-tab).
2. `GET /api/sse?client_id=new-uuid`.
3. Hub отдаёт кеш: `satellite_group_update` (таблица), `satellite_state_update` (позиции).
4. Hub вызывает `onClientConnect(new-uuid)` → `ClientStateStore.GetTracking(new-uuid)` → 0 (новый клиент, нет сопровождения).
5. Вторая вкладка показывает обзорный режим: таблица, карта, но **без** красно-зелёных трасс.

Первая вкладка продолжает вести сопровождение — её `client_id` сохранён в `ClientStateStore` с `tracking_id > 0`.

### Сценарий 4: Нет КА в зоне видимости

Ни один пролёт не попадает в скользящее окно. `FindConcurrentPasses()` возвращает пустой список. `findNearestFuturePass()` находит КА с ближайшим AOS (через 47 мин). Группа: один КА-заглушка, `IsVisible=false`. Таблица в правой панели показывает одну строку с обратным отсчётом «47:12». Карта рисует только наземную трассу этого КА (future, серый пунктир). Az/El — нулевые. Нижняя панель — «Обзор».

Когда `now` приближается к AOS (< 1 мин) — КА попадает в скользящее окно нормальным путём, IsVisible сменится на true при AOS.

### Сценарий 5: Переподключение после обрыва сети

SSE-соединение обрывается. `SSEClient` обнаруживает `readyState === CLOSED`, устанавливает статус `DISCONNECTED`, запускает reconnect с exponential backoff (1с → 2с → 4с → ... → 30с max). Индикатор SSE в station-footer становится красным.

При восстановлении:
1. Новое SSE-соединение с тем же `client_id` (из `sessionStorage`).
2. Hub отдаёт кеш — фронтенд получает актуальную группу и позиции.
3. `onClientConnect` → `ClientStateStore.GetTracking(clientID)` → tracking_id, если было сопровождение.
4. `client_state_restore {tracking_id}` — фронтенд восстанавливает tracking-слой.
5. Для оператора — мгновенное восстановление, как будто обрыва не было.

## Справочник

### SSE-события

| Событие | Частота / триггер | Кешируется Hub | Содержание |
|---------|-------------------|---------------|------------|
| `satellite_state_update` | 1/сек (позиции), 1/30 сек (+ трассы) | Да | `positions[]`, `tracks[]`, `ts` |
| `satellite_group_update` | При изменении группы или primary (≤ 1/5 сек) | Да | `satellites[]`, `primary_id`, `tracking_id`, `time_window` |
| `satellite_change` | При смене primary или сбросе tracking | Нет | `norad_id`, `name`, `reason`, `inclination`, `period` |
| `client_state_restore` | При подключении клиента или смене tracking | Нет (directed) | `tracking_id` |
